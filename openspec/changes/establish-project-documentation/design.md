## 背景

项目拥有高层 README、约 1 MB 的 `AIContext/` 历史对话导出、六月 Phase A-H 大纲、7 月 20 日状态记录，以及截至 7 月 24 日之后的实现改动。旧大纲仍把 Phase F 标为未完成、G0 标为未开始，但当前代码已经包含 Phase F、数据驱动命中判定、Server 战斗结算、格挡交互、健康 UI、方向受击、权威 HP/revision 和 NPC 快照纠正。

文档需要服务项目所有者和后续编码代理，同时避免让生成式历史记录成为竞争事实源。当前工作树已经在 Server 战斗结果中携带绝对 HP/revision，传播实际格挡与破防伤害，并增加 NPC 周期 HP 纠正；这些路径只能标为 `Implemented`，在完整 Host/Client 矩阵验收前不能标为 `Verified`。Player 快照仍缺少 NPC publisher 具备的周期 HP 纠正。

## 目标 / 非目标

**目标：**

- 创建一组无需阅读 `AIContext` 即可独立理解的规范文档。
- 描述第一方 Unity 架构以及控制、战斗、同步、表现和 UI 的主要数据流。
- 将稳定能力需求与按时间排列的 Phase A-H 交付历史分离。
- 通过明确证据记录实现、验证、延期和已知缺口。
- 让文档可以从 README 发现，并能随未来功能变更持续维护。
- 规定 OpenSpec 自然语言文档统一使用简体中文。

**非目标：**

- 修改玩法、网络、场景、预制体、ScriptableObject、包或应用代码。
- 改写、删除或整理 `AIContext` 原始对话导出。
- 把代码存在或构建通过冒充为 Play Mode 或多人验收。
- 在文档 change 中实现或运行时验证战斗网络、锁定或血条行为；本文只记录当前代码及其验证缺口。
- 将 Phase A-H 变成主要需求分类方式。

## 设计决策

### 使用四份规范文档

在 `docs/` 下维护：

- `PROJECT_OVERVIEW.md`：产品定位、技术栈、第一方目录、场景/资产、架构图和职责边界。
- `REQUIREMENTS.md`：角色控制、战斗、锁定/相机、同步、NPC AI、表现/UI、内容生产的能力需求。
- `ROADMAP_AND_PROGRESS.md`：Phase A-H 映射、当前状态、证据、延期、缺口和基线。
- `VERIFICATION_MATRIX.md`：Offline、Host、Client、本地/远端 Player 和 NPC 验收项。

未采用单一大文档，因为稳定架构与需求会随进度更新频繁抖动，验证缺口也难以扫描。

### 能力组织需求，阶段组织进度

能力域是稳定导航模型，Phase A-H 保留为历史交付视图。每个进度条目链接回相应能力。这样可避免血量 UI、方向受击和 Turn90 等跨阶段功能失去清晰归属。

### 使用明确进度词汇

进度文档只使用：

- `Implemented`：代码/资产存在，不隐含运行时验收。
- `Verified`：记录了环境和观察结果。
- `Partial`：只实现或验证了部分验收面，并明确缺失部分。
- `Deferred`：有意排除在当前完成门槛之外。
- `Not Started`：没有实质实现证据。

不使用完成百分比，因为它无法表达缺失的验收面。

### 采用证据层级

当前状态声明按以下顺序取证：

1. 当前第一方代码、场景、预制体、数据资产和 Git 历史证明实现。
2. 带日期的人工或自动记录证明验证。
3. 规范文档汇总前两类证据。
4. `AIContext` 只提供历史意图，不能覆盖更新的代码或验证证据。

需求表达预期行为，不能仅从实现反推。

### 分离实现和验证

远端 NPC 绝对 HP/revision 纠正、GuardHit/GuardBreak 实际伤害、相机朝向锁定和单一共享世界血条策略，依据当前路径记为 `Implemented` 而不是 `Verified`。Player 周期 HP 纠正和缺失的环境矩阵继续作为明确缺口。这些是进度事实，不是本 change 的实现任务。

### README 保持简洁

README 继续作为入口和快速开始指南，只链接四份规范文档并修正过时摘要，不复制完整内容。

### OpenSpec 文档统一使用中文

仓库级 `openspec/config.yaml` 为 proposal、design、specs 和 tasks 增加简体中文规则。已有 artifacts 同步翻译。为保证 CLI 校验，`ADDED/MODIFIED/REMOVED/RENAMED`、`Requirement/Scenario`、`WHEN/THEN` 等固定语法，以及代码标识符、路径和命令保留原文。

## 风险 / 权衡

- [风险] 文档在玩法提交后过时。-> 缓解：改变验收声明的 change 必须同步更新进度和验证文档。
- [风险] 历史陈述与当前行为冲突。-> 缓解：将 `AIContext` 标为历史，并在进度文档记录基线日期与提交。
- [风险] `Implemented` 被误认为已测试。-> 缓解：显式定义状态，并把验证单独放入矩阵。
- [风险] 需求文档夸大未完成能力。-> 缓解：分离目标需求和实现状态，并链接进度条目。
- [风险] 第三方目录淹没项目结构。-> 缓解：只详细描述第一方职责，第三方依赖只做摘要。
- [风险] 翻译固定 OpenSpec 语法导致 CLI 失效。-> 缓解：仅翻译自然语言，保留校验器要求的固定标记。

## 迁移计划

1. 根据当前代码、资产、Git 历史和已验证的 `AIContext` 决策创建四份规范文档。
2. 将每项进度声明与代码/资产路径、提交或验证记录交叉核对。
3. 更新 README 链接和过时摘要。
4. 增加 OpenSpec 中文规则并翻译已有 artifacts。
5. 运行 Markdown 链接检查和 OpenSpec validate。
6. 检查验证矩阵，不把未运行的项目提升为 `Verified`。

回滚只需还原文档、README 和 OpenSpec 规则；不存在运行时或序列化数据迁移。
